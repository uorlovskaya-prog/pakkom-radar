# Пакком — Радар

Управленческий дашборд. Рабочая страница: `index.html` в ветке `main`.

## Правила обновления

Новые периоды добавляются в существующую актуальную версию. Не генерировать заново интерфейс, фильтры, формулы и исторические записи. Сначала читать текущую версию `main`, чтобы не затереть доработки из другого чата. Повторную загрузку идентичного периода пропускать; конфликт с закрытыми датами останавливать и разбирать отдельно. Исторические суммы и исходные строки не изменять при исправлении группировки.

Технические описания источника, обновления и сверки, служебный CONTROL не выводить на рабочий экран. Внутренние проверки данных, дату актуальности и управленческие статусы CPO сохранять. Скрытие служебных блоков не означает, что неустранённые финансовые расхождения проверены или исправлены.

## Единый товар с номером WB и без него — обязательное правило v4

Отсутствие номера WB НЕ создаёт отдельную карточку одного товара. Недостаточно исправлять только суффикс `.0` или поиск: записи `NAME:...` и `NMID:...` должны иметь единый ключ во всей истории.

Использовать общий модуль `sku-identity-v4.js` и его встроенную копию `PAKKOM_SKU_IDENTITY_GUARD_V4` в HTML. Реестр соответствий строится по ВСЕМ загруженным датам ДО фильтрации по периоду. Одинаковое нормализованное название связывает запись без номера с единственным известным номером этого товара. Когда у ранее безномерного товара впервые появляется WB ID, вся его история отображается одной карточкой. Исходные поля и финансовые значения остаются неизменными.

Нормализация: числовые/текстовые WB ID, `.0`, регистр, повторные и неразрывные пробелы, `x`/`х`/`×` между цифрами, `50шт`/`50 шт`, `ё`/`е`. Дополнительно проверены варианты названий скатертей `зелен бел`/`зел бел` и `синяя бел`/`син бел`.

Не стирать признаки товара: размер, объём, цвет, количество в упаковке, материал и рисунок. Разные фактические WB ID не склеивать по похожим цифрам. Неоднозначное соответствие требует разбора, а не произвольного выбора. Товар без WB ID допустим: использовать один нормализованный ключ названия, а не заводить новый ключ при каждой загрузке.

Одинаковый ключ применяется к группировке, поиску по названию и номеру, раскрытию карточки, дневной/недельной истории и сигналам. Поиск по номеру обязан включать старые строки, где номер ещё отсутствовал. Перед публикацией проверять уникальность «дата + единый товар», неизменность исходных данных и отсутствие разорванной истории.

Регрессионные примеры:
- скатерти 110х140 2 шт желт бел — `1748180510`, включая 30.09.2026 без номера;
- скатерти 110х140 2 шт зел бел — `1748622323`, включая `зелен бел`;
- скатерти 110х140 2 шт син бел — `1748327732`, включая `синяя бел`;
- тарелки 23 см 50 шт зеленые — `1531061921`, включая `50шт`;
- стаканы бум 250 мл 25 шт золото — `1661578582`;
- пакеты рулон 24х37 100 шт бел пищевые — `1828990377`;
- пакеты рулон 30х40 100 шт бел пищевые — `1721217247`;
- пакеты крафт 195х90х340 v-дно 50 шт — `1556365321`.

## Публикация и проверки

Обновление файла в чате само по себе не обновляет сайт. После подготовки изменений нужны запись в этот репозиторий, успешная публикация GitHub Pages и проверка опубликованного артефакта. В ответе отдельно указывать готовность файла и статус сайта. Финансовый HTML в чате имеет отдельный интерфейс; не заменять им страницу Радара.

`.github/workflows/pakkom-sku-v4.yml` проверяет изменения `index.html`, общего модуля и самого workflow: единый ключ, поиск, отсутствие повторов по датам, сохранение количества и сумм, разделение разных размеров/цветов/фасовок. Это CI, а не фоновая загрузка отчётов. Первичное исправление применяется только к строго проверенному blob v3; после него workflow выполняет проверки без пересборки интерфейса.

Правка v4 от 09.10.2026: DATA сохранён побайтно, 6 597 дневных записей по 08.10.2026. Объединены 14 пар «с номером / без номера», 199 → 185 карточек; 39 ранее безномерных строк включены в известные товары. Оставшиеся 13 безномерных строк не имеют совпадающей карточки с номером и остаются самостоятельными товарами, а не удаляются. Повторов «дата + единый товар» нет. ## Оба сайта — один завершённый отчёт

Каждое добавление дня или периода обязательно включает оба адреса: `index.html` для Олега и `management.html` для владельца. Оба обновляются из одного проверенного полного отчёта, с одной конечной датой. Обновление только Радара не завершает задачу. Пользователь не должен отдельно напоминать об управленческом сайте.

Перед выпуском: проверить закупочную себестоимость и комплектацию каждого нового товара (нехватка данных — стоп), отсутствие дублей «дата + единый товар», совпадение новых дневных сумм с отчётом и сохранение истории. При замене оперативных сведений использовать подтверждённые новые данные; расхождения с оперативной выгрузкой на рабочие экраны и в отчёты не выводить.

Управленческий выпуск шифровать текущим публичным ключом, сохраняя весь объект `account`, вход v10, фильтры v9 и идентификацию SKU v4. Следовать `management-src/ACCESS.md`. Расшифрованный HTML и пароль не публиковать.

Обновление считается завершённым только после успешного `Check paired report dates`, успешной публикации Pages и повторного чтения ОБОИХ постоянных адресов: конечная дата должна совпадать с отчётом, опубликованные байты — с проверенными версиями. В ответе указывать готовность обоих сайтов. Проверка CI обнаруживает рассинхронизацию дат, но не загружает данные WB и не заменяет подготовку двух выпусков.

## Сумма заказов после комиссии — обязательное правило

В полном и кратком отчёте, в Radar Олега и управленческом сайте владельца показывать «Заказы после комиссии, ₽ (оценка)». Источник — поле «Заказы минус комиссия WB»: использовать его напрямую, без деления на 0,7 и без повторного вычета комиссии. Поле `ordersRub` в DATA обоих сайтов означает сумму после комиссии; `ordersAmountBasis` должно быть `after_commission`. ДРР и «Реклама / заказы» рассчитываются от этой же суммы. Фактическая ЧП остаётся расчётом по выкупам и выплатам из детализации WB.

Исправление от 20.10.2026 привело ранее показанные суммы до комиссии к согласованному виду после комиссии; исходники, количество заказов, выкупы, расходы, НДС и ЧП сохранены. При обновлении брать исправленный полный отчёт через 19.10.2026 как базу. Не умножать исправленную историю на 0,7 повторно.

## Сигналы спроса и управленческие приоритеты v11

На обоих сайтах использовать одну версию `management-signals-v11.js` и `management-src/signals-ui-v11.js`, встроенную в HTML. Исходный DATA не менять при правке сигналов. Для нового дня пересчитать сигналы из всей истории до даты последнего отчёта; не переносить готовые статусы из старого выпуска.

Проверки независимы от CPO: 2 дня к предыдущим 2, 7 дней к предыдущим 7, устойчивое падение 5 дней к тем же дням недели за две предыдущие недели и длительное снижение относительно медианы 2–4 предыдущих полных недель. Учитывать календарное покрытие и начало истории товара; не превращать пропуск отчёта в ноль. Численные пороги и минимальная база определены в общем модуле и раскрыты на сайте.

Критическое падение заказов имеет приоритет над хорошим CPO и историческим статусом «Кандидат на рост». Небольшой отскок не снимает длительное падение. Одновременно показывать все сигналы, точные интервалы, сравниваемые количества и следующие проверки. Не объявлять нехватку товара, потерю показов или ухудшение конверсии установленной причиной без соответствующих исходников. Не предлагать автоматическое расширение бюджета по одному историческому ROI.

Список «Что проверить в первую очередь» учитывает категорию и поиск, но не скрывает текущие риски из-за выбранной старой недели или фильтра CPO. Порядок: срочность, затем максимальное снижение темпа, приведённое к семи дням, затем расход рекламы. Это приоритет проверки, а не оценка гарантированно потерянных продаж или прибыли. Кнопка «Все проверки» показывает полный порядок действий, название открывает подробную карточку.

Перед выпуском запустить `node tests/management-signals-v11.cjs` и `node tests/signals-ui-v11.cjs`. Локально проверять также незашифрованный управленческий HTML, не публикуя его. Сохранить v4 идентичность SKU, v9 фильтры, v10 доступ и весь объект account. Управленческий release декларирует signalsVersion=11. Не пересобирать из старого HTML без этих исправлений.

Блок «Что проверить в первую очередь» по умолчанию свёрнут: видны заголовок, счётчики и кнопка «Показать». Кнопка «Скрыть» сворачивает весь список. Выбор сохраняется на устройстве отдельно для каждого сайта и не сбрасывается при фильтрации или обновлении данных.

## Ширина исходного интерфейса v13

Не переносить правый блок вниз на мониторах и не скрывать показатели ради уменьшения ширины. Таблицы и вложенные блоки ограничены шириной контейнера; текст переносится, ширины колонок пропорциональные. На узких мобильных экранах до 800 px допускается расположение блоков друг под другом. Изменение ширины не должно менять показатели, расчёты, сигналы или доступ.

## Один сигнал в строке и отдельное раскрытие внимания v15

Общая таблица SKU показывает ровно один самый важный сигнал: срочные риски (реклама без заказов, остановка, критическое падение, превышение максимального CPO) выше умеренных снижений и роста. Остальные сигналы сохраняются в полном объекте расчёта и участвуют во всех фильтрах. Внутри раскрытого SKU блок «Что требует внимания» по умолчанию закрыт и открывается отдельным нажатием; внутри остаются все сигналы, расчёты и действия. Ежедневная аналитика и финансовый блок справа открываются независимо от этого блока.

## Одинаковая высота блоков раскрытого SKU v16

На мониторах (ширина больше 800 px) ежедневная таблица слева занимает всю высоту правого блока, включая финансовую сводку, сценарий 80% выкупа и вывод. Высоту определяет правый блок; фиксированное ограничение 360 px не обрезает видимую часть ежедневной аналитики. Длинная история прокручивается внутри левого блока, строки не растягиваются. При изменении ширины окна высота пересчитывается средствами CSS. На мобильных экранах блоки остаются друг под другом. Отдельное раскрытие «Что требует внимания», компактные строки, один главный сигнал и фильтры по всем сигналам сохранены.

## Единый диапазон дат v17

На обоих сайтах поля «С даты» и «По дату включительно» всегда видны вверху. Можно выбрать один день, произвольный интервал, готовую неделю, начало последнего загруженного месяца, последние 7 дней или всю историю. Оба края включаются в расчёт. Неверный или ещё не загруженный диапазон показывает понятную ошибку и не заменяет последний корректный расчёт.

На управленческом сайте один диапазон применяется к KPI, общей таблице SKU, ежедневной аналитике, правой финансовой сводке, сценарию 80% выкупа и недельной детализации SKU. Неделя на границе интервала обрезается по выбранным датам и подписывается точными датами. Переключение вкладки не сбрасывает выбор. Карточки недель внутри диапазона позволяют сузить выбор, а список готовых периодов — выбрать другую неделю. По умолчанию остаётся период с 01.09.2026, вся история с августа доступна отдельной кнопкой.

Сигналы и управленческие приоритеты продолжают оценивать последние загруженные дни по всей истории, независимо от периода финансового среза. Открытие SKU из приоритетов сохраняет диапазон, если в нём есть этот товар; при отсутствии истории товара в выбранном диапазоне явно переключает поля на всю историю. Модули `management-src/date-range-ui-v17.js` и `management-src/signals-ui-v11.js` встроены в оба HTML.

Все денежные подписи заказов явно содержат «после комиссии WB»; `ordersRub` используется без повторного вычета комиссии, исходный DATA не изменён. Зафиксированный интерфейс v13–v16, все финансовые столбцы, правый блок, одинаковая высота блоков, закрытое внимание и фильтры по всем сигналам сохраняются.
